3. Our TODO — Backend We Handle Ourselves

Built by us on our stack, independent of the client's systems. Where the Cloud Kitchen API is involved we build against a mock adapter now and swap in the real API when access arrives.

  • Database & product catalog schema (products, variants, add-ons, categories, branches, orders, customers)
  • Cart & order engine (pricing, add-ons calculation, order lifecycle)
  • Admin dashboard shell — the panel that hosts CMS, CRM, and analytics
  • CMS (marketing team self-service): edit main-menu & footer links · manage hero slides (image + link) · product data (name, price, description, variants, show/hide, direct price discounts) · reorder products / featured items · view orders data (best sellers, total sales, conversion rate, sessions, order count) · view customer data (contact info, per-customer order history)
  • CRM: store customer data + phone numbers, order history per customer, export for future marketing campaigns
  • Analytics dashboard (details in §6): sales, products, marketing, branch performance
  • OTP login flow implementation (ready to plug into the SMS gateway the moment it's subscribed)
  • Payment integration layer (ready to plug into the client-provided gateway; supports sandbox first)
  • Mock Cloud-Kitchen API adapter — mirrors the interface we expect (Foodics / Matrix compatible shape) so ALL blocked features below can be developed and demoed before real access
  • Server-side tracking events (Meta CAPI, TikTok Events API) — scaffolding now, live keys later
  • Reviews fetch job (Google Reviews) — ready for the client's place IDs
  • WhatsApp notification templates & sender module — ready for WhatsApp Business API credentials
Why the mock adapter matters: it means API unavailability never blocks development. We build and demo everything against realistic fake data; connecting the real Cloud Kitchen API becomes a wiring task, not a rebuild.

5. What We Need FROM the Client — Request List

Per management: the payment gateway and the Cloud Kitchen system are provided by the client, not by us. This is the concrete list to send them. Execution starts after the proposal is approved and these are delivered.

🔌 Cloud Kitchen / POS system CLIENT PROVIDES

  • Which system are they on? (Foodics, Matrix, or other — both named as integration targets in scope)
  • API documentation + API credentials (key/token) for a test AND production environment
  • Confirmation of which endpoints exist (checklist in §4: branch menus, availability, prices, discounts, inventory, order create, order status/webhooks, delivery zones/fees/ETA, driver tracking, scheduled & reorder support)
  • A technical contact at the POS provider for integration questions

💳 Payment gateway CLIENT PROVIDES

  • Which gateway/provider (their merchant account — not ours)
  • Sandbox/test credentials, then production keys
  • Payment methods to enable (card, mobile wallet, cash on delivery)
  • Refund/void policy to reflect in the order flow

📱 SMS gateway (OTP) CLIENT PROVIDES

  • Subscription with an SMS gateway provider (required for phone + OTP login per scope)
  • Sender name registration + API credentials

💬 WhatsApp Business API CLIENT PROVIDES

  • WhatsApp Business API account (for automatic order notifications)
  • Per-branch WhatsApp numbers (for the sticky contact buttons)

📣 Ad & analytics accounts CLIENT PROVIDES

  • Meta Business Manager access (Pixel + Conversions API)
  • TikTok Ads account access (Pixel + Events API)
  • Google account access: GA4 property, Google Tag Manager, Google Ads (Enhanced Conversions)
  • Microsoft Clarity — we can create under their account

🏪 Branch & business data CLIENT PROVIDES

  • The 11 branches: addresses + map coordinates, hotline per branch, WhatsApp per branch, working hours
  • Delivery areas, fees, ETA per branch (or confirmation this comes from the POS API)
  • Google Business Profile access / place IDs (to display Google Reviews)

🎨 Brand & content CLIENT PROVIDES

  • Official brand guide / color confirmation (current palette is provisional, extracted from the logo)
  • Full menu data: product names, descriptions, prices, variants, add-on prices (photos already received)
  • Legal texts: terms of service, privacy policy, offer terms, delivery terms
  • FAQ content + any video review files

🌐 Infrastructure CLIENT PROVIDES

  • Domain name (or delegation to point DNS)
  • Hosting decision/approval (we can recommend and manage)
  • Google Maps API billing account (map display on branches page)

9. Delivery, Maintenance & Revisions

On delivery, client receives

  • Full technical documentation of the platform
  • Full access to the website source code

Client remains free to use any other developer/team for future changes — no technical lock-in to us.

Optional maintenance service covers

  • Meal updates · photo updates · price updates
  • Adding offers · content monitoring

Does NOT include code or design changes.

Revision policy: one revision round after the first version is presented. Any additional revisions or out-of-scope requests are priced separately.
